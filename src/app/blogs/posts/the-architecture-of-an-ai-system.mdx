When you use an AI application, the mental model is usually pretty simple. You type something, the AI thinks, and you get an answer.

```text
You → AI → Answer
```

That model is useful, but it is also wildly incomplete. A modern AI system is not just a model sitting on a GPU waiting for your prompt. There are applications, context builders, agent loops, tools, retrieval systems, model-serving infrastructure, GPUs, storage systems, monitoring, and an entire lifecycle that happened before you ever typed the first character.

If you are building AI applications, understanding these boundaries is more useful than memorizing a list of AI buzzwords. So let's open the box.

## The naive mental model

Start with the simplest possible architecture:

![The naive mental model: User, then AI, then Answer](/blog-images/the-architecture-of-an-ai-system/01-naive-ai-model.png)

You send a prompt to an AI, it processes it, and it returns some text. At the center of this system is a **model**, the thing that takes an input and produces an output based on the patterns it learned during training.

That raises a few questions worth sitting with. Who actually sends your prompt to the model? What exactly gets sent to it? And if you are using a coding agent, how does the model read files, run commands, search the web, call APIs, and modify your code? The model itself does not magically have access to any of these things. There is a lot more software surrounding it.

## Let's open the box

A more useful mental model looks something like this:

![The full AI system stack from User through Application, Harness, Runtime, Serving, and GPU down to the Model](/blog-images/the-architecture-of-an-ai-system/02-complete-ai-system.png)

This is not one universal implementation. Different companies combine, split, rename, or hide these components. They are still useful **architectural boundaries** for understanding how modern AI systems work.

There is another major part of the picture that does not sit underneath the GPU: the **model lifecycle**. Serving infrastructure runs a trained model. The lifecycle is how you get that model in the first place and keep improving it. Let's go through the stack from the top.

## The AI application

At the top is the thing you actually interact with. It could be a chat interface, an API, a coding environment, a customer support product, or an internal company tool. In every case, the application's job is to turn a user's interaction into something the rest of the AI system can process.

Suppose you ask:

> What is the capital of France?

The application receives that message, but the model might not receive exactly those words. There may be system instructions, conversation history, retrieved documents, tool definitions, and information about the current user or task. Someone has to construct the actual context that will eventually reach the model. That is where things start getting interesting.

## The agent and the harness

If you are building a simple chatbot, you might not need a complicated agent layer. You can essentially do `User message → Model → Answer` and stop there.

A coding agent is a different problem. You say "fix the authentication bug in my application," and the system now has to inspect the repository, find the relevant files, read the code, understand the error, decide what to change, modify files, run tests, read the output, and repeat until the task is done. The model can reason about those actions, but something has to **orchestrate the process**. That surrounding software is often described as an **agent harness**.

![Harness internals: context, tools, routing, loop, state, memory, permissions, compaction, and error recovery](/blog-images/the-architecture-of-an-ai-system/03-harness.png)

The exact implementation differs between systems. Anthropic's Claude Code and OpenAI's Codex are sophisticated coding-agent systems, and their internal architectures are proprietary, so it would be wrong to assume either one literally implements this diagram. The point is the boundary.

**The model is not the entire agent.** The harness is the software around the model that manages the interaction between the model, the environment, and the task. If you want this layer in more detail, I wrote about [building AI agents from scratch](/blogs/building-ai-agents-from-scratch).

## What does the model actually see?

This is one of the most important concepts in AI engineering. Suppose you type "fix the login bug." The model does not see your entire computer. It does not automatically see every file in your repository, know which tools exist, or magically inspect your database. Something has to construct the model's input.

![Context construction: system instructions, history, user message, retrieved context, tools, and state become the model input](/blog-images/the-architecture-of-an-ai-system/06-context-construction.png)

This is why **context engineering** matters so much. The model can only reason over the information that is actually made available to it. And that brings us to one of the most common pieces of AI application architecture.

## Retrieval and RAG

Suppose your company has 50,000 internal documents and you ask, "What is our refund policy for enterprise customers?" You probably don't want to put all 50,000 documents into the model's context. Instead, the system can retrieve the pieces of information that are relevant to the question. That is the basic idea behind **Retrieval-Augmented Generation**, or RAG.

There are two different flows to understand.

![RAG has two flows: ingestion into a vector database on the left, and query-time retrieval on the right](/blog-images/the-architecture-of-an-ai-system/05-rag.png)

Before anyone asks a question, documents are split into smaller chunks, each chunk is converted into a numerical representation called an **embedding**, and those embeddings are stored alongside the original content and metadata.

```text
Document chunk:  "Enterprise refunds are..."
Embedding:       [0.12, -0.44, 0.83, ...]
Metadata:        document_id=123, department=billing
```

A vector database can then search for vectors that are close to the vector representing a user's query. The important thing to understand is that **RAG does not retrain the model**. The model remains the model. RAG changes the information that is supplied to it at request time.

This is also why a vector database is not the same thing as a key-value store or a graph database. A key-value database answers `key → value`. A vector database answers "find things similar to this vector." A graph database is optimized around relationships: Alice works at a company, the company owns a product, the product depends on a service. Different storage models exist because different questions require different retrieval mechanisms.

## Tool calling

Retrieval lets an AI system **find information**. But what if it needs to **do something**?

Suppose you ask, "What is the weather in New York?" The model does not need today's weather baked into its weights. The application can expose a weather tool, the model can request it, and the surrounding software can actually call the API.

```text
User → Model → "I need weather data"
             → Tool call → Weather API
             → Tool result → Model → Answer
```

The model generates a structured request representing the tool it wants to use. The surrounding software interprets that request and executes it. That distinction matters. **The model can request an action. The surrounding system performs the action.**

The tool could be a weather API, a database query, a web search, a shell command, a file operation, a payment API, a Git operation, or an internal company service. The model does not need to implement any of those capabilities itself. It needs a way to express that it wants one of them.

## MCP, tools, and the harness

This is also where people often mix up several different concepts. A **tool** is an action the AI system can invoke. An **MCP server** can provide tools and other capabilities to an AI application through the Model Context Protocol. A **harness** is the surrounding orchestration layer that manages the model interaction, context, tools, state, permissions, and execution. They are related, but they are not interchangeable terms.

```text
                 HARNESS
                    │
          ┌─────────┴─────────┐
          │                   │
       MODEL                TOOLS
                              │
                     ┌────────┼────────┐
                     │        │        │
                   Files     APIs    Database
```

MCP can be one mechanism for making tools or other capabilities available to the application. It is not itself an agent, it is not the model, and it is not synonymous with a harness.

## The agent loop

Now we can finally explain what makes something feel like an agent. A simple model interaction is `User → Model → Answer`. An agentic interaction has a loop: the model can call a tool, receive the result, reason again, and either call another tool or stop.

![The agent loop: User to Harness to Model, then Tool call, Tool, Tool result back to the Model, or a stop to Final answer](/blog-images/the-architecture-of-an-ai-system/04-agent-loop.png)

The model receives the result of the tool, reasons again, and might call another one. That result comes back, it reasons again, and eventually it decides it has enough information to produce a final answer. A useful engineering abstraction is:

```text
Agent = Model + Tools + State + Loop + Stop Condition
```

This isn't the only possible definition of an agent, but it is a useful way to reason about agentic systems as an engineer. The **loop** is the part that matters. Without it, you have `Input → Model → Output`. With it, the model can either emit a final answer or request another action. That is the basic machinery behind many systems that people casually call "AI agents."

## The AI runtime

So far we've mostly talked about what happens around the model. Eventually the system still has to actually **run** it. Call that layer the **AI runtime**, or the inference platform. It can own request management, routing, authentication, rate limiting, guardrails, policy enforcement, caching, sandboxing, observability, model selection, and scheduling. The exact mix depends on the architecture.

This distinction matters because **inference** and the platform around inference are not the same thing. Inference means running the trained model to produce an output. The platform around it can include a lot of other responsibilities.

## Model serving

Now we are getting closer to the actual computation. A model-serving system is responsible for running inference efficiently at scale. If thousands of users send requests at the same time, you don't want each request to grab an entire GPU and run independently. Modern serving systems have to manage resources carefully, which is where **batching**, **scheduling**, **GPU memory**, **KV cache**, and the tradeoff between **throughput and latency** start to matter.

There is another useful distinction inside inference itself. When a prompt first arrives, the system has to process the input tokens. That is commonly called **prefill**. Then the model generates output tokens one at a time. That is the **decode** phase.

![Model serving path on the left, prefill and decode on the right](/blog-images/the-architecture-of-an-ai-system/07-inference-serving.png)

The model repeatedly predicts the next token. That sounds simple. The hardware and systems engineering required to do this efficiently at large scale is not.

## What actually happens on the GPU?

At the lowest level of this request path, we eventually reach hardware. A GPU performs the enormous amount of numerical computation that modern neural networks require. The model contains parameters, those parameters are numerical values, and inference is the process of applying them to the input through many layers of computation.

```text
Tokens
  → Embeddings
  → Transformer layers
      → Attention
      → Feed-forward computation
      → Normalization
  → Output probabilities
  → Next token
```

For a language model, this process happens repeatedly as new tokens are generated. The important thing is that **the GPU is not the model**. The GPU is hardware. The model is the learned mathematical structure represented by its architecture and parameters. The serving system loads that model onto the available hardware and executes it.

## The model itself

So what is the model? At a high level, you can think of it as architecture plus parameters plus weights: a trained model. For a modern language model, the architecture defines how information flows through the network, and the parameters are the learned numerical values used during inference to turn input into predictions.

```text
Input tokens → Model → Probability distribution → Next token → Repeat
```

The model does not need a file system, a browser, a Git repository, or your company's database to predict the next token. Those capabilities come from the software surrounding it. That distinction becomes extremely important once you start building AI systems.

## Where did the model come from?

There is another entire system behind the model. Before it can serve your request, someone had to create it.

![Model lifecycle from data and training through evaluation, post-training, release, deployment, monitoring, and iteration](/blog-images/the-architecture-of-an-ai-system/08-model-lifecycle.png)

Models need enormous amounts of training data, and that data has to be collected, processed, filtered, transformed, and prepared. During training, the model's parameters are optimized using large amounts of computation, which is where massive GPU clusters and distributed training systems become important. Evaluation is how you measure whether any of that worked, through general benchmarks, task-specific tests, safety evaluations, human review, and internal suites.

A base model can then be further trained or optimized for particular behaviors. That post-training step includes techniques such as supervised fine-tuning and preference-based optimization. Once a model is ready, it has to be packaged and deployed into a serving environment. After users start sending requests, you monitor latency, errors, throughput, resource utilization, quality, safety, and cost, and eventually you learn enough to improve the next version.

This entire loop is part of the broader **MLOps and model lifecycle**.

## What changes for a coding agent?

Let's follow the authentication example one more time. You ask the system to fix the authentication bug. The application passes that request into the agent, the harness constructs context, and the model receives the relevant instructions, conversation, tool definitions, and available state.

The model might decide it needs to inspect the repository and produce a tool call. The harness executes that tool, the file contents come back, and the model analyzes them. It might request another file, then another, then modify something and run tests. If the tests fail, the result goes back into the loop, the model reasons again, and the process continues until a stop condition is reached.

This is why calling the model itself "the coding agent" is misleading. The model is a critical component, but the useful behavior emerges from the **system around the model**.

## The bigger lesson

This way of looking at AI systems changes how you think about AI engineering. Instead of asking which framework to use, you can start asking which part of the system you are actually building.

If the problem is retrieval, you are thinking about chunking, embeddings, vector search, reranking, metadata, and context construction. If it is tool use, you are thinking about schemas, execution, permissions, failures, and structured outputs. If it is agentic behavior, you are thinking about state, loops, stop conditions, context management, and recovery. If it is serving, you are in batching, scheduling, GPU memory, KV cache, throughput, latency, and inference engines. If it is the model itself, you are talking about architecture, training, evaluation, post-training, and weights.

These are very different engineering problems, and they live at different layers.

## You don't need to build every layer

There is one final thing worth emphasizing. You do not need to build all of this yourself. Most AI engineers are not training a foundation model from scratch, most application developers are not writing GPU kernels, and most teams are not building their own inference engine. You can consume these layers as services.

```text
Your Application → Agent / Harness → Model API → Someone else's AI infrastructure
```

Or you might control more of the stack:

```text
Your Application → Your Agent → Your Serving Layer → Your GPU Cluster → Your Model
```

The abstraction boundary is a choice. That is exactly how software engineering has always worked. You don't need to build your own database to build a backend, you don't need to build your own operating system to build a web server, and you don't need to train your own foundation model to build an AI application. What matters is understanding **where the boundary is and what happens across it**.
